# Security Controls

A finance company's workloads warrant defense-in-depth. This is what's
implemented, layer by layer.

## Network layer
- Only the ALB sits in public subnets; ECS tasks and Aurora are in private
  subnets with no direct route to the internet.
- DB subnets have **no** route to an Internet Gateway or NAT Gateway at all —
  a compromised app-tier task cannot use the database subnet as an egress path.
- Security groups are chained least-privilege: Internet → ALB SG (80/443) →
  App SG (app port, ALB SG only) → DB SG (3306, App SG only). Nothing else in
  the VPC can reach the app or DB tier directly.
- VPC Flow Logs are enabled and shipped to CloudWatch Logs for network-level
  audit trail (`ALL` traffic type — accepted and rejected).

## Edge / application layer
- AWS WAF (regional Web ACL) attached to the ALB: AWS Managed Common Rule Set,
  Known Bad Inputs, SQL injection rule set, plus a rate-based rule
  (2,000 requests/5min per source IP by default) to blunt basic volumetric abuse.
- ALB has `drop_invalid_header_fields` enabled and (optionally) enforces
  TLS 1.2+ via `ELBSecurityPolicy-TLS13-1-2-2021-06` when a certificate is supplied.

## Identity & access
- ECS task **execution role** (pulls image, writes logs, reads the one secret
  it needs) is separate from the ECS **task role** (what the running
  application code itself can call) — least privilege in both directions.
- No long-lived credentials anywhere in the stack: DB password is generated by
  Terraform (`random_password`), stored only in Secrets Manager, and injected
  into the container at runtime via ECS `secrets`, never as a plain env var in
  the task definition.
- RDS enhanced monitoring and Performance Insights use their own scoped IAM role.

## Data layer
- Aurora storage is encrypted at rest via a dedicated customer-managed KMS key
  with rotation enabled.
- Automated backups (7-day retention by default), a defined backup window,
  and `deletion_protection` turned on automatically for any environment named
  `prod`.
- Audit, error, and slow-query logs are exported to CloudWatch Logs.

## Secrets management
- Database credentials live only in AWS Secrets Manager, generated by
  Terraform at apply time — never committed to source control, never in
  `terraform.tfvars` (which is gitignored), never printed in outputs
  (the RDS endpoint output is marked `sensitive`).

## Supply chain
- ECR repository is created with `scanOnPush=true` so every pushed image is
  scanned for known CVEs before it can be deployed.
- Base image pinned to `node:20-alpine` (small attack surface, few packages).

## Things intentionally left as follow-ups (documented, not silently skipped)
- **AWS Config / Security Hub / GuardDuty** are not enabled in this submission
  to keep the stack focused on the stated requirements, but would be the next
  addition for a real finance-sector production account (config drift
  detection, threat detection, compliance scoring).
- **Private ECR endpoint / VPC endpoints for Secrets Manager, ECR, S3, CloudWatch**
  are not included; traffic currently egresses via NAT Gateway. Adding
  interface VPC endpoints would remove that NAT dependency for AWS API calls
  and reduce data-exfiltration surface further — recommended as a fast-follow
  since it's a pure networking/IAM addition with no app changes.
- **Cross-account backup/DR** (e.g., replicating Aurora snapshots to a second
  AWS account) is out of scope here but would be a reasonable ask for a
  finance company's DR posture.
